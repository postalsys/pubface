# Claude Development Guidelines

## Project Overview

pubface resolves the public-facing network interfaces of the current machine.
For each non-internal local interface it makes an outbound HTTPS request (bound
to that local address) to a resolver service - by default
`https://api.nodemailer.com/` - to learn the public IP address the outside world
sees, then performs a reverse-DNS (PTR) lookup on that IP. It returns an array of
`{ localAddress, ip, name, family, defaultInterface }` entries.

It is written in TypeScript under `src/` and published as a dual package:
ES modules in `dist/esm/` and CommonJS in `dist/cjs/`, each with type
declarations. Both `require('pubface')` and `import { resolvePublicInterfaces } from 'pubface'`
work. The layout follows `../nodemailer` and `../imapflow`.

It ships in two forms:

- A module exposing `resolvePublicInterfaces()` (and the `PublicInterface` type).
- A `pubface` CLI that prints the resolved interfaces as JSON, also distributed
  as prebuilt standalone binaries. The `bin` entry is the CommonJS build
  (`dist/cjs/cli.js`), the format pkg can bundle.

pubface is a dependency of EmailEngine (`../emailengine`), which loads it with
`require('pubface')` and whose tests replace `resolvePublicInterfaces` on the
module object, so that export must stay a plain writable property.

## Project Structure

- `src/index.ts` - Main module. Public interface detection, DNS/PTR resolution, the
  outbound HTTPS resolver request, and result merging and sorting
  (`combineResults`). Exports `resolvePublicInterfaces`, the `PublicInterface`
  type, a default export object, and an `_internal` object used only by the tests
  (tagged `@internal`, so it is stripped from the declarations).
- `src/cli.ts` - CLI entry point (calls `resolvePublicInterfaces` and prints JSON).
- `src/package-info.ts` - Generated by `scripts/build.js` from `package.json`
  (`name`, `version`). Gitignored and regenerated by `npm run build` and
  `npm run typecheck`. Never import `package.json` from `src/`.
- `scripts/build.js` - The build: generates `src/package-info.ts`, runs `tsc` with
  `tsconfig.esm.json` and `tsconfig.cjs.json`, writes a `package.json` with the
  module format into each output directory. The CommonJS output is used as tsc
  emits it (no default-export rewrite as in imapflow, nothing here needs one).
- `scripts/mutation-test.js` - Mutation testing (see Testing).
- `scripts/pkg-smoke.js` - Builds a pkg binary for the host and runs it (see Testing).
- `dist/` - Build output, gitignored; it is what gets published to npm.
- `test/` - TypeScript tests (`*.test.ts`), run with `node --import tsx --test`.
  `test/package/` checks the built `dist/` output, its exports and declarations;
  `test/cli.test.ts` runs the built CLI; `test/fixtures/` holds the resolver
  certificate, the shared resolver stand-in (`resolver-server.cjs`, plain CommonJS so
  the smoke scripts can load it too), the DNS cache helpers and the fuzz generators.
- `eslint.config.js` - Flat ESLint config, the shared baseline used across
  Postal Systems packages (`../nodemailer/eslint.config.js` is the canonical form;
  only the "Repo-specific" block may differ). `src/` is also linted with the
  type-aware rules.
- `.prettierrc.cjs` / `.prettierignore` - Shared Prettier config (printWidth 160,
  tabWidth 4, single quotes).
- `package.json` - Also holds the `pkg` build configuration (binary targets).

## Technology Stack

- **Language**: TypeScript (`tsconfig.base.json`: strict, `exactOptionalPropertyTypes`,
  `erasableSyntaxOnly`, `isolatedModules`, `stripInternal`), compiled twice from the
  same sources. `@types/node` stays on the 20.x line and `typescript` on 6.x
  (`.ncurc.cjs`).
- **Dependencies**: `ipaddr.js` (IP parsing). The bound outbound HTTPS request uses
  `node:https` directly, so `localAddress` and the pinned resolver IP reach the socket
  and the certificate is verified against the resolver hostname.
- **License**: MIT No Attribution (MIT-0)

## Module format

- Source uses ES module syntax and every file compiles both ways, so code under
  `src/` must not use `import.meta`, `require`, `module`, `exports`, `__dirname`,
  `__filename`, top-level `await`, or JSON imports.
- `erasableSyntaxOnly` is on: no enums, no namespaces with runtime code, no
  parameter properties.
- Relative imports carry the `.js` extension. Node builtins are imported with the
  `node:` prefix as default imports (`import dns from 'node:dns'`) and their methods
  are called through that object at call time, so tests can stub them with
  `mock.method()`.
- Public API functions are declared in `src/index.ts` itself (`export async function`),
  not re-exported from another module: tsc emits a re-export as a getter, which a
  CommonJS consumer can not overwrite.
- Every optional property of a public interface is declared with an explicit
  `| undefined`, so consumers compiling with `exactOptionalPropertyTypes` can pass
  a value that may be undefined.

## Testing

- Uses the Node.js native test runner (`node:test`) with `node:assert/strict`,
  through `tsx`. Run a single file with `node --import tsx --test test/resolve-ip.test.ts`,
  or a single test by name with `--test-name-pattern="<name>"`.
- `npm test` builds first (`pretest`), because `test/package/` and `test/cli.test.ts`
  load the built `dist/` output.
- CI (`.github/workflows/test.yaml`) runs lint, format:check and the tests on
  Node 20, 22, 24 and latest (coverage on 24), `npm run test:cjs` on Node 22+,
  and `npm run test:pkg` in a separate job.
- Tests are hermetic: network, DNS, and `os.networkInterfaces()` are mocked via
  `node:test` mocks, the resolver is an in-process HTTPS server with the fixture
  certificate (`test/fixtures/resolver.crt`, valid for `resolver.test`, `127.0.0.1`
  and `::1`), and the CLI tests preload `test/fixtures/stub-dns.cjs` and trust the
  fixture through `NODE_EXTRA_CA_CERTS`. Keep them that way - new tests must not
  depend on real DNS or the live resolver service.
- Seeded property tests (`test/fuzz.test.ts`, generators in `test/fixtures/fuzz.ts`)
  check PTR names for every textual form of random addresses, IP extraction from
  arbitrary JSON bodies, timeout parsing, the invariants of `combineResults`, and
  random or broken raw HTTP responses from the resolver. A failure names its seed,
  reproduce with `FUZZ_SEED=<seed>`; raise `FUZZ_ITERATIONS` (default 500) for a soak run.
- `npm run test:mutation` applies one-operator mutants to `src/index.ts` in private
  copies of the repository and lists those no test catches. Run it after larger
  changes and add a test for a surviving mutant or confirm it is equivalent. Two
  known equivalents: the `>=` of the DNS cache expiry check (a 1 ms boundary), and
  `client === https` before setting `servername` (Node 24 derives the same name from
  the Host header; the Node 22 case it guards against is only reachable over IPv6,
  whose HTTPS test skips there).
- Helper functions are exported through `_internal` purely so the tests can
  exercise them; this object is not part of the public API.

## Packaging (@yao-pkg/pkg)

We package pubface into standalone executables with
[`@yao-pkg/pkg`](https://github.com/yao-pkg/pkg) (the maintained fork of the now
unmaintained `vercel/pkg`). The build configuration and target list live under
the `pkg` key in `package.json`; binaries target Node 24 for Linux x64, macOS
x64, macOS arm64, and Windows x64 and are written to `ee-dist/`.

**`@yao-pkg/pkg` only supports CommonJS**, both for these binaries and for
EmailEngine's, which bundles pubface as a dependency. See Platform constraints.

## Platform constraints

pubface reaches runtime inside two `@yao-pkg/pkg` binaries: its own CLI builds
and EmailEngine's. pkg snapshots a CommonJS module graph and cannot load ES
modules, and EmailEngine's DigitalOcean one-click images update EmailEngine but
never the Node.js under it. Two rules follow:

- **Node.js 20 is the minimum.** Code, tests and tooling must work on Node 20, 22
  and 24 (`engines.node` is `>=20.0.0`). The binaries embed Node 24, but the npm
  package runs on whatever Node the consumer has.
- **Everything that reaches runtime must be genuinely CommonJS-loadable.** The
  project's own code and every runtime dependency must load through `require()`
  with `--no-experimental-require-module`. A CommonJS entry that only wraps a
  dynamic `import()` of ESM code does not count. A pure-ESM dependency breaks the
  binary even though plain `node` runs it: Node 22+ (and 20.19) load ES modules
  through `require()` by default, which hides the problem.
- **Keep the dual build.** Never drop the CommonJS output, make the CommonJS entry
  depend on ESM-only syntax, or point `bin` at the ES module build.
- **How to check:** `npm run test:cjs` requires the built CommonJS entry and runs a
  lookup with `NODE_OPTIONS=--no-experimental-require-module` (plain JavaScript on
  purpose: tsx's loader would mask an ES module dependency); CI runs it on Node 22+.
  `npm run test:pkg` builds and runs a real pkg binary. Run both after any
  dependency change.
- **Pinning:** never add or upgrade to an ESM-only dependency. Add the package to
  `.ncurc.cjs` (`reject`, or a `target` that keeps the last CommonJS major) with a
  comment giving the reason.

## Dependency Management

- `npm run update` removes `node_modules` and `package-lock.json`, runs
  `ncu -u` (npm-check-updates) to bump every dependency to its latest allowed
  version, then reinstalls.
- `.ncurc.cjs` controls which upgrades `ncu` is allowed to take. Add any package
  whose newer releases are pure ESM (or otherwise break the `@yao-pkg/pkg` build
  or our supported Node range) to its `reject` list, with a comment explaining
  why, so it stays pinned to its last compatible release.
- After updating dependencies, run `npm run lint`, `npm test`,
  `npm run test:cjs` and `npm run test:pkg`, and remember that production dependency changes are
  user-facing - commit them with a `fix:` prefix so a release is cut (see Commit
  Conventions).

## Releases

- Releases are managed by `release-please` (config in `release-please-config.json`
  and `.release-please-manifest.json`), driven by Conventional Commit messages on
  `master`.
- On a release, the `release` workflow publishes to npm with provenance
  (`npm publish --provenance --access public`).
- Prebuilt CLI binaries are built locally with `npm run build-dist` and attached
  to the GitHub release.
- The `prepare` script builds `dist/` on install and before publish, so build
  output is never committed.

## Code Style Rules

- Never use emojis in code or documentation, only printable ASCII characters.
- Use a single hyphen-minus (`-`) as a dash in UI copy and user-facing strings.
  Never use double hyphens (`--`), em dashes, or en dashes.
- The library is TypeScript with ES module syntax under `src/`, compiled to both
  formats (see Module format). Plain JavaScript files outside `src/` follow the
  package `"type": "module"`, except `.cjs` files (configs, the CommonJS smoke test).

## Commit Conventions

- Use [Conventional Commits](https://www.conventionalcommits.org/) - `feat:`,
  `fix:`, `chore:`, `docs:`, etc. `release-please` relies on these prefixes to
  decide version bumps and changelog entries.
- When composing git commit messages, do not include Claude as a co-contributor.
- For commits that do not change runtime behavior (docs, comments, CI/workflow
  tweaks, formatting), append `[skip ci]` to the commit message to avoid
  triggering the GitHub Actions workflows. Exception: do not add `[skip ci]` to
  commits using a `fix:` or `feat:` prefix - those must run so the release action
  is triggered.

## After Making Code Changes

1. Run `npm run format` and `npm run lint` (CI also runs `npm run format:check`).
2. Run `npm test` and make sure the suite passes.
3. Consider `/simplify` to review changed code and `/security-review` to check
   for security issues before committing.
4. After pushing, check the GitHub Actions runs for the push (for example
   `gh run list --branch <branch>`) and report their status, including CodeQL. If
   a run fails for a strange or unrelated reason (for example a checkout step
   reporting "account suspended", HTTP 403, or other auth/infrastructure errors
   that have nothing to do with the change), check <https://www.githubstatus.com/>
   for an active GitHub incident before assuming the failure is caused by the
   change.
